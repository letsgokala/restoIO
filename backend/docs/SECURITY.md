# Security foundation

- Staff passwords are hashed with Argon2id; responses never contain password hashes.
- Sessions use 256-bit random opaque secrets. The API stores a SHA-256 token digest, expires sessions, and revokes on logout.
- Cookies are HTTP-only, `SameSite=Strict`, scoped to `/api/v1`, and `Secure` in production. Staff tokens are not stored in browser local storage.
- Login and public restaurant registration request bodies are Zod-validated and rate-limited. Registration is limited to five attempts per IP per hour and passwords must have at least 12 characters. Request bodies are size-limited.
- Helmet applies security headers; CORS allows the configured web origin with credentials.
- Unsafe browser requests with an `Origin` are checked against the configured origin. SameSite cookies provide a further CSRF boundary.
- Tenant endpoints require a restaurant context and check active restaurant and branch memberships in the backend. Owners have restaurant-wide scope even when their initial account was created from a branch-scoped seed assignment. Branch-scoped management checks prevent a manager from targeting another branch's tables by guessing a record ID. Database composite foreign keys prevent associating a branch with the wrong restaurant.
- Errors use stable codes and request IDs. Unexpected error details are not returned to clients.
- QR resolution compares SHA-256 digests and verifies that the QR, table, branch, and restaurant are active and that an optional expiry is still valid before returning public restaurant/table fields. Internal database IDs are omitted from public DTOs. Issued raw tokens are returned once at creation; an AES-256-GCM encrypted copy lets authorized restaurant managers reprint an active code. Set a persistent, random `QR_TOKEN_ENCRYPTION_KEY` in production. Changing it makes stored codes unreadable for reprinting; the QR tokens can then be rotated. The development seed uses a fixed, predictable demo QR; it must never be used outside local development.
- Guest checkout requires an idempotency key and a separate random guest access token. Only its digest is stored with the order. The raw token is sent as a request header for checkout retry and returned only in a scoped HTTP-only, SameSite=Strict order cookie. Tracking requires that cookie and a valid expiry; order references alone do not authorize reads.
- Guest assistance tracking uses a separate random 256-bit token, stores only its digest and expiry, and returns it in an HTTP-only SameSite=Strict cookie scoped to that request's status endpoint. A request reference by itself does not authorize status reads; guest responses omit staff identities and internal tenant IDs.
- Checkout reloads item availability and modifier selections and recomputes all prices with Decimal values. It ignores client totals. The row lock on the table serializes session reuse, while a unique idempotency key prevents duplicate creation.
- Guest QR, checkout, tracking, and assistance endpoints use in-process rate limits. Assistance also limits repeated requests for a table and request kind. A shared limiter store is required before horizontal scaling.
- The waiter dashboard requires an active `WAITER` membership and tenant/branch context; its order and assistance lists are filtered server-side. Status transitions validate the actor's role, current order state, tenant and branch, and persist the acting staff identity. Rejecting an order requires a reason. Order closure requires paid status and does not close the table session.
- The kitchen queue and mutation routes require an active `KITCHEN` membership and tenant/branch context. The queue is filtered in the repository and excludes guest tokens, customer notes, payment state, and prices. Kitchen users cannot use the shared status endpoint to skip item workflow, serve, or close orders. Item readiness is tenant/branch-scoped and transactionally audited; an order becomes READY only when all its items are ready. Cancelling a confirmed or preparing order requires an audited reason and appears in the kitchen change feed.
- Cashier routes use restaurant-role checks that explicitly do not inherit the platform-admin tenant bypass. CASHIER, owner, or manager membership is required; every query scopes by restaurant and selected branch. Payment amounts use Prisma Decimal, the session row is locked before outstanding balance is read, and serializable transactions enforce no overpayment under concurrent requests. Idempotency keys are unique, payment records are retained, and a manager/owner void requires a reason and creates an audit event. Session closure checks remaining balance and served/closed/cancelled/rejected states in one transaction. Kitchen and waiter roles cannot record or inspect payments.
- Analytics routes are limited to restaurant owner/manager memberships and apply the authorized tenant/branch scope in the repository. Platform restaurant listing and status changes require explicit platform-admin authentication; restaurant owner requests are denied by the backend.
- Production environment loading now requires an explicit database URL, HTTPS web origin, and stable QR encryption key of at least 32 bytes. Production cookies are `Secure`, `HttpOnly`, and `SameSite=Strict`.
- Guest order tracking polls only the caller's cookie-authorized order. Staff dashboard polling is authenticated and branch-scoped; no Socket.IO broadcast is used.
- Development seed credentials are configurable, local-only, and seed execution refuses `NODE_ENV=production`. Never copy development values into a deployed environment.

## Current limitations

Restaurant owners can self-register, but email verification, bot protection, and password reset are not configured. Add those controls before broadly advertising open registration. Owners create staff credentials directly. Rate limits use the Express process memory store and need a shared store if the API is horizontally scaled. Origin validation permits non-browser clients without an `Origin`; production deployments should additionally enforce trusted ingress/network policy. External push notifications are not configured; dashboards receive updates through polling, and waiter assistance notices are dashboard-local.

The payment provider contract is defined in `src/modules/payments/providers`, but no provider adapter is registered. Chapa's official flow requires server-side transaction verification and signed webhook validation; see [Accept Payments](https://developer.chapa.co/integrations/accept-payments), [Verify Payments](https://developer.chapa.co/integrations/verify-payments), and [Webhooks](https://developer.chapa.co/integrations/webhooks). Ethio telecom's [Telebirr developer portal](https://developer.ethiotelecom.et/user/product) describes separate integration products and testbed credentials; select and validate the merchant's exact H5/web integration before implementing signatures or callback rules. Merchant sandbox access and credentials are not available in this local project. Do not mark any provider-originated payment successful until an adapter verifies its callback and server-side transaction details against the persisted intent.
