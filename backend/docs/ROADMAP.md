# Roadmap

1. **Phase 1 — Foundation:** implemented: web/API apps, initial database schema and migrations, staff auth, tenant scope, local seed, checks and documentation.
2. **Phase 2 — Restaurant management:** implemented: restaurant onboarding and settings, tenant-scoped branch/staff/table management, role-based permissions, encrypted QR issuance/rotation/revocation and printable sheets, menu categories/items, branch availability, reviewed translations, and modifiers. The management workspace is `/manage`. See the API and local demo steps in `backend/README.md`.
3. **Phase 3 — Customer application:** verified and implemented: guest QR entry, branch-aware menu availability, seven UI locales, cart/customization, server-priced checkout, idempotency, shared table sessions, private order and assistance tracking, and customer assistance requests. Browser coverage includes a second isolated guest ordering to the same open table session, waiter processing, customer status polling, and assistance acknowledgements. See `docs/PHASE3_VERIFICATION.md` for the audit scope and test evidence. Socket.IO is absent; polling is the synchronization path.
4. **Phase 4 — Waiter dashboard:** implemented: branch-scoped waiter workspace, polling order queue, order review/accept/reject with reason, audited role transitions, table/session aggregation, assistance handling, history, and customer status synchronization. Playwright coverage follows a guest order through service. See the waiter demo credentials and API endpoints in `backend/README.md`.
5. **Phase 5 — Kitchen display:** implemented: role- and branch-scoped `/kitchen` workspace, accepted-order queue, audited item readiness, all-items-ready aggregation, cancellation change feed, and polling synchronization with waiter and guest order tracking. See `backend/README.md` for the kitchen demo and API.
6. **Core completion — offline cashier and reports:** implemented: Decimal payment ledger, partial payments, consolidated session billing, audited voids, cashier UI, branch/date filtered reports, platform account lifecycle, and branch operating hours. See the manual testing guide.
7. **Online providers and production operations:** Chapa/Telebirr provider contract is scaffolded, but online execution remains disabled pending credentials and a tested callback flow. Managed image storage, account recovery/invitations, shared rate-limit storage, centralized monitoring, production deployment automation, and external backup operations remain incomplete.
8. **Phase 8 — Advanced:** loyalty, promotions, reservations, inventory, advanced analytics and AI-assisted discovery.

Guest, waiter, kitchen, offline cashier, platform account, and initial reporting flows use database records. Public cafe requests are pending until platform approval, and the first platform administrator is bootstrapped through a one-time token. Socket.IO is not used; staff dashboards and guest status views poll the API and refresh when a tab returns to the foreground. Remaining launch work includes verified email and approval notifications, bot protection, password reset/invitations, shared rate-limit storage, centralized monitoring, managed image storage, and tested online provider callbacks. QR codes need a stable `QR_TOKEN_ENCRYPTION_KEY`; rotate it only with a planned QR reissue because it is needed to display/reprint active codes.
